# 事件雷达 · 投资事件情报与证据时间线

> 同一投资事件会以公告、新闻、研报观点和市场传闻等形式持续演化。本产品帮助用户看清：事件的最初来源、事实变化、证据冲突、当前状态，以及与关注标的的关系。

**在线演示**：https://event-radar-fcy0.onrender.com （Render 免费实例，首次访问有约 30-60 秒冷启动）

---

## 一、目标用户与要解决的问题

**目标用户**：A 股个人投资者与中小型投研团队，需要跟踪"正在发生的事"而非"已经定价的事"。

**非目标**：不做行情预测、不输出买卖建议、不替代公告原文阅读。

**核心问题**：投资者面对同一事件的多个信息源时，有三个高频痛点：

1. **说不清"现在信什么"**——传闻、媒体报道、公司澄清、监管公告混杂，投资者难以区分哪条是事实、哪条是传言，结论随最新一条信息漂移；
2. **丢了时间维度**——事件发生时间、披露时间、抓取时间常被混淆，导致"旧闻当新闻"；
3. **无法追溯**——结论不知道依据哪份原始材料，无法核对。

**为什么需要 LLM**：同一事件的识别（"成飞借壳成飞集成"与"成飞借壳中航电测"是同一大事件的两个命题）、事实/观点/推测/传闻四分类、原文证据抽取，都需要语义理解；规则引擎只能做关键词兜底。

## 二、核心设计

### 主链路（全链路可在线操作）

```
文档入库(4个时间戳) → LLM 主张抽取 → 同一事件识别与合并 → 命题归并与判定
→ 版本演化(结论快照) → 状态机更新 → 用户通知 → 合规检查
```

- **四个时间戳**：事件发生时间（event_time，来自正文）、披露时间（disclose_time，来自信源）、抓取时间（crawl_time，入库时刻）、更新时间（updated_at，结论每次变化时刻）。每篇文档与每个事件都完整记录。
- **四分类与证据权重**：每条主张标记为 事实 / 观点 / 推测 / 传闻；证据权重 = 来源权威度（公告 5 > 权威媒体 3.5 > 一般媒体 2.5 > 社交媒体 1）× 声明类型系数，与来源逐条绑定、可点击回原文。
- **同一事件识别**：两级策略——规则打分（主体交集 + 事件关键词桶）明确匹配或新建；灰区交给 LLM 判定合并/新建（含降级规则）。同一事件下按"核心命题"归并，如「成飞集团借壳成飞集成」与「成飞集团借壳中航电测」同属一个事件的两个命题，各自独立判定。
- **判定状态机**：`传闻阶段 → 发展中 → 已证实/已否认/已更正/证据冲突/已完结 → 已过期`。
  优先级：证据冲突 > 完结 > 更正 > 否认 ≈ 证实（证实与否认同优先级互斥才构成"证据冲突"，完结/更正会取代低优先级判定）。
- **版本演化**：每次证据入库都生成版本记录（v1, v2, …），包含变化类型与结论前后快照，可回溯任意时点的结论。
- **结论翻转与通知**：官方否认、更正、完结、证据冲突、过期时，事件结论即时更新并推送通知（🔔 通知中心），明确"依据哪份文档、在何时、从什么变成了什么"。

### 结论表达与合规边界

- 结论由模板生成：`截至{披露时间}，事件状态为【X】。命题A：判定（依据：来源，时间，证据权重）…证据构成：事实n条/观点n条/推测n条/传闻n条`；
- **不输出**确定性涨跌预测、收益承诺或买卖建议（含建议性用语的清洗器 + 全量结论断言测试）；
- 每一条主张都保留原文逐字引用（quote 字段）与来源链接，关键结论可回溯到原始字段或原文；
- LLM 接口失败时降级为规则抽取并显式标记 `⚠ 接口降级`，绝不静默生成"正常"结论。

## 三、AI 的角色

| 环节 | AI 做什么 | 降级路径 |
|---|---|---|
| 主张抽取 | 从文档中抽取 1-4 条主张：四分类、一句话归纳、**逐字原文引用**、涉事主体、事件时间、核心命题 | 本地缓存 → 关键词规则抽取（标记 degraded） |
| 同一事件合并 | 规则打分后的灰区，判定"并入哪个事件还是新建"并给理由 | 主体/话题交集规则 |
| 结论生成 | 不参与（模板化，保证确定性与合规） | — |

抽取结果全部落盘缓存（`data/extracted/`），演示环境可离线回放、结果可审计。详见 [AI_USAGE.md](AI_USAGE.md)。

- 金融数据优先使用 iFinD MCP / 扶摇 API 的可用能力；演示数据为题目允许的公开权威材料兜底（见 AI_USAGE.md 数据来源核对表），来源、披露时间均在入库时记录；
- 生产扩展：iFinD MCP 公告/新闻/研报接入层（`POST /api/documents` 与数据源注册表已预留）、扶摇行情用于"事件影响验证"辅线；
- 不采集、不存储任何用户持仓/隐私数据。

## 五、快速开始

```bash
# 1. 安装依赖（Python 3.10+）
pip install -r requirements.txt

# 2. 配置环境变量（复制 .env.example 为 .env，填入 DEEPSEEK_API_KEY）
cp .env.example .env

# 3. 引导演示数据（按披露时间顺序回放 31 篇文档，LLM 抽取并缓存）
python -m scripts.bootstrap_demo            # 实时 LLM 抽取（失败自动降级）
python -m scripts.bootstrap_demo --offline  # 仅用缓存抽取结果

# 4. 启动服务
uvicorn app.main:app --host 0.0.0.0 --port 8000
# 打开 http://localhost:8000
```

**在线操作主链路**：页面右上角「+ 提交新文档」——粘贴任意一篇公告/新闻，实时完成 入库 → 抽取 → 合并 → 判定 → 通知，观察事件结论是否翻转。

**测试**：

```bash
python -m pytest tests/ -v   # 17 个用例，覆盖主链路 / 数据与接口异常 / 合规边界
```

## 六、已知边界与未做事项

**已知边界**
- 事件合并的别名表（主体别名、事件关键词桶）目前仅覆盖演示事件的领域范围，生产需接入工商知识库/证券代码库；
- 规则降级模式的抽取精度显著低于 LLM，仅用于接口异常时保证链路可用；
- "过期"阈值固定为 60 天，未做按事件类型差异化；
- 权威媒体对官方结论的转载（如新华社报道韩国学会结论）按"权威媒体"而非"官方公告"计权，可能低估个别证据权重；
- 演示数据为历史真实事件；系统未接入实时行情，暂不做"事件-价格"影响验证辅线。

**未做事项**
- 用户自定义订阅/关注清单与推送渠道（邮件/短信/App）；
- 研报观点批量抽取与分析师级证据画像；
- 事件相关性推荐（"与您关注标的相关的 3 个事件"）；
- iFinD MCP / 扶摇 API 的实时数据源接入（接口层已预留）；
- 事件合并的向量检索（当前为规则+LLM 判定两级）。

## 七、项目结构

```
app/            # config / db / llm(抽取+合并判定) / compliance(合规) / pipeline(主链路) / main(FastAPI)
data/raw/       # 31 篇真实公开文档（UTF-8 JSON，含 URL/披露时间/正文）
data/extracted/ # LLM 抽取结果缓存（可审计、可离线回放）
web/            # 无构建步骤的 SPA（原生 JS，深色终端风格）
scripts/        # bootstrap_demo.py 演示数据回放
tests/          # pytest：主链路 / 接口异常 / 合规边界
```
